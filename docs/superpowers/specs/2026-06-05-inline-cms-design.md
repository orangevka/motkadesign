# Простая inline-CMS для motka.ru — дизайн

**Дата:** 2026-06-05
**Статус:** спецификация, утверждена пользователем (ожидает финального ревью)

## Цель

Дать возможность редактировать текст в существующих блоках сайта прямо на
странице: авторизованный пользователь кликает по текстовому блоку и правит
текст на месте. Без сторонних библиотек и без отдельной тяжёлой админки.

## Контекст проекта (ограничения, формирующие дизайн)

- Сайт **статический** (HTML/CSS/JS, экспорт из Webflow).
- Прод `motka.ru` обновляется **автодеплоем 1:1**: пуш в git → `rsync`
  перезаписывает файлы на сервере.
- На сервере **есть PHP** (на нём работает бэкенд формы заявки).
- Есть механизм исключения папок из деплоя (папка `local/` с robots,
  защита папки `tuna`) — файлы там не перезатираются деплоем.

Главное следствие: правки нельзя хранить прямо в HTML на сервере — следующий
деплой их затрёт. Поэтому контент выносится в отдельное хранилище вне git.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Что редактируем | **Только текст** в существующих блоках (не картинки, не структура) |
| Где хранятся правки | **JSON-файл на сервере, вне git** (деплой его не трогает) |
| Охват первой версии | **Одна страница-пилот** — на **копии** `services`, прод не трогаем |
| Вход | **Один общий пароль** + PHP-сессия |
| Источник текста | **HTML — база, JSON — оверрайд** (пока блок не тронут в CMS — показывается текст из HTML) |
| Редактор | **Inline `contenteditable`** — клик по блоку правит на месте |

## Архитектура

### Что в git (код, деплоится как обычно)

1. **`assets/local/cms.js`** — клиентский скрипт, подключается на страницах:
   - На **любой** загрузке: подтягивает JSON с контентом и для каждого
     размеченного блока, по которому есть запись, подменяет текст (оверрайд).
     Нет записи → остаётся текст из HTML.
   - Если есть активная сессия редактора: включает режим правки —
     клик по блоку делает его `contenteditable`, показывает плавающую
     панель с кнопками «Сохранить» / «Выйти».

2. **`cms/login.php`** — форма входа: проверяет пароль (сверяет с хешем),
   ставит PHP-сессию. CSRF-токен.

3. **`cms/save.php`** — принимает правки и пишет в JSON. Работает только при
   активной сессии. Принимает ключи **только из заранее разрешённого списка**.

4. **Разметка пилотной страницы** — нужным текстовым блокам проставляется
   атрибут `data-cms="<уникальный-ключ>"`.

### Что вне git (на сервере, деплой не перезатирает — папка `local/`)

5. **`local/cms-content.json`** — сам отредактированный контент:
   `{ "<ключ>": "<текст>", ... }`.

6. **`local/cms-config.php`** — хеш пароля (не сам пароль) + соль CSRF.

## Потоки данных

### Чтение (любой посетитель)

```
Загрузка страницы
  → cms.js fetch local/cms-content.json
  → для каждого [data-cms] с записью в JSON: element.textContent = запись
  → блоки без записи остаются как в HTML
```

### Запись (авторизованный редактор)

```
Вход на cms/login.php (пароль) → PHP-сессия
  → на странице cms.js видит сессию → включает режим правки
  → клик по [data-cms] → contenteditable
  → «Сохранить» → POST cms/save.php { ключ: textContent, csrf }
  → save.php проверяет сессию + ключ в whitelist → пишет в cms-content.json
  → правка видна сразу всем
```

## Безопасность (минимум по делу)

- Храним и подставляем **только текст** (`textContent`, не `innerHTML`) —
  убирает риск инъекции разметки/скриптов.
- `save.php` принимает ключи **только из whitelist** — нельзя записать
  произвольный ключ.
- **CSRF-токен** на операцию сохранения.
- Пароль хранится как **хеш** в файле вне git.
- Сессия проверяется на каждом сохранении.

## Границы первой версии (YAGNI — НЕ делаем)

- Картинки и медиа.
- Добавление / удаление / перестановка блоков.
- Несколько пользователей и роли.
- История версий / откат.
- Возврат правок в git.
- Rich-text (жирный, ссылки и т.п.) — только plain text.

Если пилот приживётся — расширение обсуждается отдельно, своим циклом
спек → план → реализация.

## Пилотная страница

Пилот делаем на **копии** страницы `services`, а не на боевом файле — прод
не трогаем, всё отрабатываем на копии. Боевой `services` подключаем к CMS
только после того, как механика проверена и устраивает.

- Копия живёт отдельным файлом (имя/URL — решим в плане, напр. `services-cms.html`).
- Копию закрываем от индексации (noindex / robots), чтобы не попала в выдачу.

## Открытые вопросы для реализации (решим в плане)

- Точное имя/URL файла-копии и как закрыть его от индексации.
- Точный путь и имя whitelisted-ключей (схема именования `<page>.<block>`).
- Куда физически класть `cms/*.php` относительно docroot и как защитить
  `local/` от прямого HTTP-доступа к `cms-config.php`.
